  • 心理状态：压力值、折磨类型、怪癖、死亡之门经历
  • 拿到了什么：战利品清单、任务结算奖励

✘ 拿不到（需要取舍）

  • 精确伤害数值（「造成 17 点伤害」）——日志不写
  • 技能名——不记录用了哪个技能
  • 命中/闪避的逐次判定——只记录暴击，不记录 miss
  • 奇物的具体交互文本——只记结果类型，不给过程
  • 实时血量曲线——只能拿到存档快照，不是逐帧

这些不是死路：要么用文学化措辞绕过（「一记重击，白骨碎裂」），要么走路线 B（内存读取）补全，代价见第 4 节。

02为什么必须做成「外部挂载程序」，而不是一个 Mod

这是整件事最关键的结构性判断，也是很多人一上手就走错的地方。

《暗黑地牢》的 Mod 体系是纯数据替换：mod 目录里放 project.xml 加上镜像游戏目录的 .darkest / .json / .string_table 文件，游戏启动时覆盖加载。它没有任何脚本层——没有 Lua、没有 C#、没有事件回调、没有 Mod API。你能改数值、改文案、换贴图、加角色，但你不能写一行代码在「暴击发生时」做任何事。

所以「在游戏里实时插入 AI 生成的段落」这条路，靠 Mod 是走不通的。能走的只有两种：

  • 从进程外面看（读日志、读存档、读内存）→ 用一个独立窗口把文字盖在游戏上。这是推荐路线。
  • 从进程里面改（DLL 注入 + 内存读写 + hook 渲染层）→ 理论上能真的把文字画进游戏 UI，但这是逆向工程量级，且每次游戏更新、每加一个 mod 都可能崩。

补充一个冷知识：游戏自带 -enabledebuginput 启动参数，开启后按功能键可以在屏幕上直接显示血量、压力、火把、出手顺序的数字。这证明这些数据在内存里是现成的、可读的——只是游戏不打算给程序看，只给人看。

04粒度设计：不是「每回合写一次」

这是最容易做砸的地方。如果每打一回合就调一次模型，你会得到：延迟打断节奏、大量重复、以及「他一剑砍下去，造成了 12 点伤害」这种流水账。

正确做法是三级粒度，和小说本身的层次对应：

层级触发时机内容长度
节拍 beat每次暴击 / 濒死 / 崩溃 / 陷阱不调模型。只在本地记一行，作为素材0
场景 scene一场战斗结束 / 一次扎营 / 一次奇物交互「这一战发生了什么」，含人物心理300–500 字
章节 chapter副本结算（胜/败/撤退）整趟探索的收束，呼应前几章600–900 字

按你 10:25 那局的数据量：6 场战斗 + 1 次结算 = 7 次调用，一晚上打 8 局也就 60 次左右。（估算：单次输入约 1500 token、输出约 600 token，按 deepseek-chat 的量级，一晚成本在一元以内。用本地 Ollama 跑 qwen 系列则免费，但中文哥特语感会明显弱一档。）

05Prompt 的三层结构（你的第 2 条要求）

① 世界圣经 · 你说了算

你手写的设定文件，塞进 system prompt，优先级最高。用来纠正模型对世界观的误解：这个 mod 里的「星火·灾星」是什么来头、赤羽隼人这个自制职业的来历、你的队伍之间是什么关系。

可以随游戏进程增量更新：比如「御影在第 12 周崩溃过一次，之后怕蜘蛛」。

② 事实清单 · 程序生成

程序输出的结构化事实（就是第 1 节那段），只给事实、不给文风，明确要求「不得编造未出现的角色、敌人、物品、胜负」。

这一层是防止 AI 瞎编的关键——把「创作自由」限制在修辞层面，而不是事实层面。

③ 文风约束 · 可调档

哥特程度、人称、是否允许角色内心独白、是否用「你」称呼玩家、每段长度、是否模仿先祖的口吻……全部做成界面上的滑杆或选项。默认给一套「先祖回忆录」风格：第三人称、冷峻、克制、结尾一句点题。

10坑在哪里（我会重点防这些）

数据侧的坑

  • 日志无限增长：现在 30MB/天。必须按字节偏移增量读，不能整文件重扫。
  • 日志有二进制脏字节：中文名附近偶有 NUL，解码要容错。
  • RNG 噪声：单条战斗日志里 90% 是随机数调试行，必须过滤，否则 token 成本爆炸。
  • mod 缺名：你会看到 nullptr、### 这类名字，需要兜底映射表。
  • 存档是二进制：需 Java 解码器（你机器上已有 Java 8）。游戏运行时可能占用文件，要容错重试。

叙事侧的坑

  • AI 瞎编：最常见的失败——凭空多出一个敌人、写死一个没死的英雄。必须用「只许用事实清单」硬约束。
  • 重复：同一场战斗被写两遍。靠场景 id 去重 + 已写内容回灌。
  • 节奏：写太长打断游戏，写太短没味道。所以做成可调长度。
  • 模型波动：同一个 prompt 出文质量不稳，需要「重写这一段」按钮。

三条你需要知道的边界

  • 不会封号。单机游戏，不改存档、不注入进程、不联机（屠夫竞技场除外，别在那用）。
  • 上不了创意工坊。工坊只收数据 mod；这类程序只能发 Nexus / GitHub。Red Hook 对同人创作态度宽松（官网有 mod showcase），但不要打包分发游戏素材。
  • API Key 存在本地。程序只从你本机读 key，不经过任何中间服务器——这是设计底线。

11还有三件事需要开一局验证

我今天没法在你打副本的时候抓数据（游戏已退出）。这三项会影响最终体验上限，但不影响可行性结论：

  1. 副本中途的存档快照：persist.game.json 里有个 raid_save 字段，非副本状态是空的。如果副本中每回合（日志里每回合都有一次 bs_save 状态跳转）它都会被填充，那我们就能拿到逐回合的血量、压力、火把、背包——这是质的飞跃。开一局，我在旁边每秒抓一次文件就能确认。
  2. 奇物交互结果的可读性：curio_tracker 里存的是哈希，需要名称表（我已经生成好 3046 条映射）才能还原成「用圣水净化了雕像，得到了……」。
  3. 伤害数值能否间接推算：日志不写伤害，但如果 raid_save 可用，逐回合血量差就是伤害。这条能救回来。

B直接把原型做完：接模型 + 覆盖窗 + 世界圣经编辑一个能边玩边看书的可用程序（第 2 步的交付物）
C先只做「编年史」：不做实时，每局结束生成一章最省事、最稳、最容易坚持的版本，一天能成型

我的建议是 A → C → B：先用一局把数据上限摸清（半小时），然后做一个「不打断游戏」的编年史版本（当天可用），确认你真的会读它，再上实时覆盖层。倒过来做——先写实时再验证内容——最容易做出一堆没人看的代码。

关于「我不会编程」这件事。这件事的真实门槛不是语法，是「能不能把问题描述清楚、能不能验收结果」。你刚才那段需求描述，已经比很多程序员写给自己的需求文档清楚。剩下的工作（写代码、查文档、改 bug、打包 exe）可以直接交给我——你说要什么效果，我改给你，你只需要负责「这个读起来对不对味」。
